Survey Form App

1. Project identity
Stack: Python 3.12+ (pyproject.toml requires >=3.12; CI/target is 3.12), Django 5, HTMX, django-htmx, SQLite (dev) / PostgreSQL 16 (prod-ready config), Tailwind CSS, pytest-django, hypothesis, ruff, black.
Demonstrates: Domain modeling for polymorphic survey schemas, repository pattern in a Django app, service-class orchestration (SurveyRunner), signed tokens via django.core.signing, HTMX-driven server-rendered wizard, branching logic with explicit BranchRule table, custom QuerySets, ADR-driven decisions.

3. App shape
Two distinct flows under one app:

Admin flow uses Django admin (no custom UI) to create surveys, questions, choices, and branch rules. Decision documented in ADR.
Respondent flow is a custom HTMX-driven wizard at /s/<slug>/step/<n>/. One question per page, server-rendered, progress bar, draft-save automatic, resume via signed token link.
Results flow is a custom admin-only page (gated by is_staff) at /admin-results/<survey_id>/ showing aggregates per question and a raw response browser.

4. Architecture principles

Admin uses Django admin. Saves budget for the parts that demonstrate architecture (engine, repositories, runner, branching). ADR-worthy decision.
Repository pattern. All data access for surveys and responses flows through SurveyRepository and ResponseRepository. Models stay dumb; managers expose QuerySets used by the repositories, not directly by views.
Service-class orchestration. A SurveyRunner instance owns the wizard state machine: which step, what's next given the branch rules, whether complete, how to save.
Server is the source of truth. No JS state. The URL /s/<slug>/step/<n>/ is the wizard's position. Back/forward work because they're real navigations.
Typed-column polymorphism on Answer (text/number/date/choice columns), not JSON. Queryable with normal SQL, indexable, honest about the polymorphism. ADR-worthy.
Branching as data, not code. BranchRule(question, choice, next_question) rows drive the runner. No if-trees in code.
Respondent identity via UUID. A Response has a uuid field; the signed resume token wraps it; the session caches it for the current visit.
HTMX-aware views. Each wizard step renders a full page on direct navigation, an HTMX partial on in-app submit.

5. Data model
Survey

id, title, slug (unique), intro (TextField, blank), is_published (bool, default False)
created_at, updated_at
Meta.ordering = ["-created_at"]

Question

id, survey (FK, CASCADE), text (TextField), order (PositiveIntegerField)
type — TextChoices: short_text, long_text, single_choice, multiple_choice, rating, likert, date, number
is_required (bool, default True)
Meta.ordering = ["order"], unique constraint on (survey, order)

Choice

id, question (FK, CASCADE), label, order
Used by single_choice, multiple_choice, rating (1–5), likert (5-point) — seeded automatically for rating/likert by admin save signal
Meta.ordering = ["order"]

BranchRule

id, question (FK, CASCADE), choice (FK to Choice, CASCADE), next_question (FK to Question, CASCADE)
Absence of a rule for a given (question, choice) means "go to the question with the next order"
Unique constraint on (question, choice)
Only applicable to single-choice questions in v2; documented in ADR (multi-choice branching would need set logic)

Response

id, uuid (UUIDField, unique, default uuid4)
survey (FK, CASCADE)
current_step (PositiveIntegerField, default 1) — stores the current Question.order (not a 1-based index); set to first_question_order on start
started_at, completed_at (nullable)
is_complete (computed property: completed_at is not None)

Answer

id, response (FK, CASCADE), question (FK, CASCADE)
text_value (TextField, blank)
number_value (DecimalField, nullable) — used by rating and number
date_value (DateField, nullable)
choice (FK to Choice, nullable, SET_NULL) — used by single_choice
choices (M2M to Choice, blank) — used by multiple_choice
created_at, updated_at
Meta.constraints: unique (response, question)
clean() enforces: only the column(s) allowed for the question's type are set (forbidden columns must be empty); it does not require a non-empty value for optional questions

7. SurveyRunner (apps/surveys/runners.py)
class SurveyRunner:
    def __init__(self, survey: Survey, response: Response, *, record: bool = True):
        self.survey = survey
        self.response = response
        self.record = record   # False for admin preview mode

    def current_question(self) -> Question | None: ...  # question at response.current_step
    def question_for_step(self, step: int) -> Question | None: ...
    def step_number(self) -> int: ...
    def total_questions(self) -> int: ...  # for "Question N of ~Total"
    def progress_percent(self, step: int) -> int: ...
    def form_for(self, question: Question, *, data=None) -> Form: ...
    def submit(self, payload: dict, *, step: int | None = None) -> SubmitResult: ...
    def next_question(self, question: Question, answered_choice: Choice | None) -> Question | None: ...
    def has_next_step(self, question: Question) -> bool: ...
    def is_final_step(self, question: Question) -> bool: ...
    def is_complete(self) -> bool: ...
The runner owns the state machine. Views build a runner from a (survey, response) pair and call methods on it. Branching logic lives in next_question() — consult BranchRule for the answered choice; fall back to next-by-order.
SubmitResult is a frozen dataclass: {ok, form, question, next_question, is_final}; .errors mirrors form.errors; .next_step is next_question.order.
8. Dynamic forms (apps/surveys/forms.py)
def form_for_question(question: Question, *, data=None, instance: Answer | None = None) -> forms.Form: ...
Maps each Question.type to a Form with one field configured with the right widget, validators, and required state. Choices are pulled from question.choices.all(). Returns a bound or unbound form per request shape. Used by both the wizard and admin preview.
9. Signed resume tokens (apps/surveys/tokens.py)
def issue_resume_token(response: Response) -> str:
    return signing.dumps({"r": str(response.uuid), "s": response.survey_id}, salt="survey.resume")

def verify_resume_token(token: str, *, max_age: int = 60 * 60 * 24 * 30) -> dict | None:
    try:
        return signing.loads(token, salt="survey.resume", max_age=max_age)
    except signing.BadSignature:
        return None

Default expiry: 30 days
Resume link shape: /s/<slug>/resume/<token>/
On valid token: load Response by UUID, set session cookie, redirect to step/<current_step>/
On invalid/expired: friendly error page with "start over" link
Resume link is generated and shown on every step's page (copy-to-clipboard), and on the "you can come back later" confirmation when a step is saved
ADR 0003 covers django.core.signing vs JWT vs homegrown HMAC

10. URLs
GET  /                                   → list of published surveys (or marketing page)
GET  /s/<slug>/                          → survey intro page + "Start" button
POST /s/<slug>/start/                    → create Response, redirect to first question order
GET  /s/<slug>/step/<n>/                 → render step n (n = Question.order; session path stack)
POST /s/<slug>/step/<n>/                 → submit step n, runner decides next URL
GET  /s/<slug>/step/<n>/back/            → go to previous question in session path
GET  /s/<slug>/resume/<token>/           → validate token, restore session, redirect to current step
GET  /s/<slug>/done/                     → completion page (requires session + completed response)

# Preview (staff only)

GET  /s/<slug>/preview/step/<n>/         → preview step n
POST /s/<slug>/preview/step/<n>/         → preview submit (computes next, no Answer write)
GET  /s/<slug>/preview/step/<n>/back/    → preview back navigation

# Results (staff only)
GET  /admin-results/<survey_id>/         → aggregates dashboard

12. HTMX patterns

Direct GET /s/<slug>/step/<n>/ → full page render
HTMX POST /s/<slug>/step/<n>/ from the "Next" button → returns the next step partial swapped into the wizard container (hx-target="#wizard", hx-swap="innerHTML")
hx-push-url on each step submit so the URL stays correct
Back navigation uses GET .../step/<n>/back/ and a session path stack (not history.back)
HX-Trigger response header for the "draft saved" toast after each step submit
hx-confirm on the "Start over" button on the resume-invalid page

13. Progress bar

Shows "Question N of ~Total" where Total = survey.questions.count()
The "~" is rendered as a subtle marker (e.g., the count in muted text) because branching makes the true remaining path unknowable without future answers
ADR 0006 documents the deliberate imprecision

14. Admin preview mode

A "Preview" action button on Survey admin → opens /s/<slug>/preview/
SurveyRunner instantiated with record=False
Form validation runs normally; submit advances the wizard but writes no Answer rows
Preview Response is in-memory only (a dummy Response object, never saved)
Preview UI shows a yellow banner "Preview mode — nothing is being recorded"
Gated by request.user.is_staff at the view level

15. Results page

Counts per question, computed via aggregators.py (one function per question type)
Choice / single-choice / multi-choice / rating / likert: counts + horizontal bar chart rendered as inline SVG (no JS chart library — server-rendered SVG is correct here and a portfolio talking point)
Rating / number: min, max, mean, median; inline SVG distribution bars (_aggregate_number.html — fixed 1–5 scale for rating, observed values for plain number)
Text (short / long): latest responses on the dashboard; full text search lives on the raw results page (HTMX, paginated)
Date: counts grouped by week (bar list in _aggregate_date.html)
Response count, completion rate (completed / started), median completion time
CSV export: one row per Response, columns = questions in order; multi-choice answers as semicolon-joined labels
JSON export: nested — {response: {..., answers: [{question, value}, ...]}}

16. Custom QuerySets / Managers
In apps/surveys/managers.py:

SurveyQuerySet.published() → filter(is_published=True)
ResponseQuerySet.complete() → filter(completed_at__isnull=False)
ResponseQuerySet.for_survey(survey) → filter(survey=survey)
AnswerQuerySet.for_question(question) → filter(question=question)

Repositories use these; views never do.
